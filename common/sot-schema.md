# sot：结构化实体层最小 schema（备而不填）

> 状态：未启用。等出现"反查 / 多跳 / 引用一致性"的真实需求再落地。
> workbench 踩过 CroForma/CUE 过度工程的坑（数十实体规模下学习与维护成本不抵收益），所以这里只备一个轻量 schema，不预先建。[验证]（workbench 2026-05-19 降级结论）

## 何时才启用

不是"想要结构化"就建。触发条件是其一真实出现：

- 要按实体反查（谁 own 什么、A 依赖 B、汇报树）。
- 要做多跳（依赖闭包、影响面）。
- 要查引用一致性（悬空引用、该有却缺）。

在那之前，实体关系用 memory 叙事写就够，不进 sot。

## 最小机制（领域无关）

源是 yaml，一个 stdlib 脚本做查询 + 校验，无编译步骤。

- **实体**：`id`（kebab）+ `type`（实体类别，领域定义）+ 类型化字段。一个字段 `profile_doc` 单向指向 memory 里的叙事条目——sot 存骨架（稳定结构事实），memory 存叙事（可独立演化），memory 不反指 sot。
- **边**：`id → id` 的有向、类型化引用。边类型由领域定义（如 reports_to / owns / depends_on）。机制只规定"边是类型化的 id 引用"。
- **校验**（脚本，退出码区分严重度）：
  - 悬空引用（指向不存在的 id）→ 硬失败（exit 1）。
  - "该有却缺"（按领域规则，如关键实体缺 owner）→ warning，不阻断。
- **维护环**：改 yaml → 跑 `check`（失败非零退出）→ commit，git diff 即 review。关系没确证就留空，不臆造。

## 非目标（显式声明，避免重蹈过度工程）

- 单时间戳，无 bi-temporal（不记"什么时候起生效"）。
- 全手工，无自动同步。
- 实体类别由领域包定义，基座不预设（基座只给"实体 + 类型化边 + 悬空校验 + backref"四件套）。

## 落点

启用时：领域包 `packs/<域>/sot/`（yaml + 校验脚本），与该域 knowledge 同级。基座这里只放 schema 约定，不放数据。[待验证]（packs 分层在 desktron 尚未落地，见 AGENTS.md 三层粒度）
