# Settings and updates

The settings page brings together this machine's environment and management entry points. It uses the same sidebar and content layout as Arrangements, Apps, and Agents.

| Setting | What it manages |
| --- | --- |
| Appearance and behavior | Display and interaction preferences |
| AI engines | Installation, login, model-related configuration, and status |
| Network and proxy | Windows connection method, proxy address, and port; see [Network and proxy](network-proxy.md) |
| Browser control | Configuration for the browser and Agent operations |
| Phone connection | Connect to Desk over trusted Wi-Fi or Tailscale by scanning a code or copying a link |
| Work tools | Installation and login status of tools such as lark-cli |
| System arrangements | Background jobs that run with Desk and their status |
| First-run setup | Rerun the environment and login checks |
| Token usage | Local model usage by date, workflow, and session |
| Task statistics | Statistics on task states |
| Debug | Debug information and the entry point to logs |

Token usage reads the provider usage returned by each engine and stores only numbers, times, engine, model, and attribution identifiers locally; it does not copy prompts, reply text, or tool arguments. Statistics can be drilled down from date to workflow, session, and individual turn; after a session is deleted its attribution is no longer shown, an anonymous total is kept, and session text is not restored. Usage from old records is listed separately as historical reference; outliers are isolated and not counted in the trusted total. When input and output breakdowns are missing, the breakdown coverage is shown instead of estimates.

Desk's appearance controls only the workbench and native windows. The built-in browser has no switch to force dark mode on web pages; page content is left to each site, which avoids inverted colors breaking images, documents, and natively dark pages.

## Interface language

Choose "简体中文 / English" in "Settings → Appearance and behavior" or in the header of the first-run setup page. The preference is stored in the current browser or device; switching does not reload the page and does not change user content, login state, or running tasks.

The interface language also sets the prompt language for sessions created afterwards. With English selected, new sessions use the English system prompt, skill instructions, and this English guide; existing sessions keep the language they were created with and do not change when you switch, and branches keep the language of their original session. Sessions created by the backend, such as arrangements and Feishu Bots, use the language the interface reported most recently. Session titles, recaps, and project memory generated by the model do not follow the language setting yet.

Coverage currently includes the main navigation, the settings and first-run screens that have been connected, the operation terminal, usage, and similar pages. User content, and raw errors from engines or the backend that are not connected to translation, stay in their original language; not every screen is guaranteed to be translated.

## Trying it on a phone over the local network

On Windows/Mac, in "Settings → Phone connection → Local network settings", tick "Enable trusted local network entry", choose this machine's private IPv4 address/prefix (for example `192.168.1.10/24`), save, and restart Desk. If network adapter detection fails, you are told so explicitly and can fill it in by hand; the server verifies that the address really belongs to this machine and refuses public, loopback, or Tailscale 100.64/10 addresses. An access token is generated automatically the first time; the private configuration is stored in `~/.config/desktron/lan.json` and must not be published or committed to a repository.

Desk listens on port 7765 on both the loopback address and the selected local network address, and accepts only this machine and the given subnet as sources. Native windows keep using the loopback entry; local network requests without the correct token are refused, except health probes. The settings page distinguishes saved configuration from actual listening state, and does not restart automatically or change the Windows firewall; if the phone cannot connect, check the trusted Wi-Fi, network isolation, and firewall rules.

On the computer itself, scan the QR code in "Settings → Phone connection", or click "Copy connection link" and open it in the phone's browser. The QR code is generated locally without an external QR service; the QR code and link are shown only on this machine's loopback entry, and the phone shows only the connection status. No connection QR code is generated when the entry is not open or listening failed. The first visit sets an HttpOnly cookie and then redirects to an address without the token. The connection page is open only on this machine's loopback entry; other devices cannot read the token. HTTP is not encrypted and is only suitable for temporary trials on a trusted local network; do not map the port to the public internet. An explicit `DESKTRON_REMOTE_BIND=all/0.0.0.0/any` also requires an access token; without one Desk refuses to start rather than falling back to unauthenticated listening on all adapters.

To turn it off, untick it, save, and restart Desk; saving a disabled setting does not immediately revoke a running listener. The listening subnet and access token are fixed when the backend starts, so saving configuration for other entry points does not suddenly change the token for a paired phone. When the adapter address changes, the local network listener reports an explicit error while the local entry keeps working; reconfigure the address and restart. Phone layout, model calls, and recovery after disconnection need to be accepted on a real device.

The old `DESKTRON_REMOTE_BIND=lan:<private IPv4>/<prefix>` environment variable still works and takes precedence, and the settings page shows it read-only. The old access token still comes from `DESKTRON_REMOTE_TOKEN` in `~/.config/desktron/env`; do not publish it. To turn off the old method, change it to `loopback` and restart.

## Phone connection through Tailscale (HTTPS)

Both the Windows/Mac computer and the phone need Tailscale installed and signed in to the same account. Desk does not install Tailscale or change its Serve configuration automatically.

1. On the computer, open "Settings → Phone connection", tick "Enable dedicated Tailscale entry", keep the default local forwarding port `7766`, and save. The port must be 1024-65535 and must differ from Desk's local port.
2. Restart Desk through the normal restart procedure. Saving by itself does not restart or start a new listener; the interface distinguishes saved configuration from actual listening state. A private access token is generated automatically the first time and stored in `~/.config/desktron/tailscale.json` in your user directory; it is not shown in the settings save response. The dedicated entry listens only on `127.0.0.1`, and generating a token does not open the local network.
3. Run `tailscale serve --bg http://127.0.0.1:7766` in a local terminal. On Windows the settings page provides a PowerShell command with the full CLI path, for cases where it is installed but PATH has not taken effect. If the domain or port already has another Serve service, check the configuration first rather than overwriting it.
4. Click "Refresh status" and scan the "Tailscale connection (HTTPS)" QR code. Not installed, not signed in, Serve not pointing at Desk, and failure to read status are all reported explicitly; a read failure is never disguised as "not configured".

An existing `DESKTRON_SERVE_PORT` environment variable or `~/.config/desktron/env` configuration keeps working; the settings page marks it as externally managed and does not overwrite the old value. When the main entry is explicitly configured to listen on all adapters, change it to `loopback` by hand before using this panel.

Requests forwarded through Serve appear to Desk to come from this machine, so this entry does not trust local origin: business requests must carry the access token, with public read exceptions only for the identity probe and the home screen icon; without a configured token the entry refuses to start. After the first scan, an HttpOnly cookie with the `Secure` flag is set, and afterwards you can open the address directly; in the phone's browser you can add it to the home screen. The local-machine checks reserved for deployment scripts and the connection page credentials are not open on this entry either.

The settings page generates a connection link only when the matching port has an HTTPS listener forwarding to Desk; with no listener or with HTTP it shows "not configured yet". If the QR code component fails to load, an explicit error is shown; copying the link does not depend on the QR code loading.

Use only `tailscale serve`, never `tailscale funnel`: the latter exposes Desk to the internet. When Funnel is detected in the configuration, Desk refuses to generate a pairing link and asks you to close the public entry first; this does not replace Tailscale's own access control and network acceptance. The phone cannot connect while the computer is asleep.

To turn it off, untick it, save, and restart Desk; saving a disabled setting does not immediately revoke a running entry or token, and with the old environment variable method you must remove `DESKTRON_SERVE_PORT` and restart. Desk never runs a global `tailscale serve reset`, to avoid clearing other services. The QR code, copied link, and actual phone access still need to be accepted on the target device.

## Updates and when changes take effect

The macOS release can check for, download, and install updates on the settings page. After you confirm an in-app update on macOS, the new version is prepared first, then the native host stops the current backend and switches the payload and desktop app; if the new version fails its startup check, the old version is restored automatically. If uninterruptible external write operations are found during preparation, the update does not start.

Windows does not support in-app updates yet; quit the app and run the new installer, see [First-run setup](first-run.md#windows). That installation flow does not have the full update and startup-failure rollback guarantees held by the macOS host described above.

A source development environment shows "Development · source sync" and does not download or install release packages. The setting's hint shows both the payload and host versions; if they differ, the code and the desktop shell have not taken effect together and need the development sync procedure.

Refreshing front-end resources and restarting the backend process are different operations. Whether a change needs a restart depends on which layer it is in; code having been synced does not mean the running Python or native shell has loaded the new version.

An ordinary restart replaces only the backend, supervised by the native Supervisor on macOS/Windows or by systemd on Linux, without waiting for all sessions to finish. History is restored from persistent records, unconfirmed tools are not rerun automatically, and external write operations still in progress may block the restart.

Restarting interrupts terminals and Agents in the process. In a shared environment, take stock of the shared tree first, then sync and restart only after explicit authorization. Product releases, runtime code sync, and user data sync are handled separately and do not substitute for one another.

Fault reports should give both the installed version and the time of the fault; see [Logs and fault reports](diagnostics.md).
